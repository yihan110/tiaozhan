## 2. 拿来主义分析（Reference + Adaptation）

> 这是最重要的评分项。我没有闭门造车，下面 4 个来源都是真实存在、可点开的项目/论文/标准。

### 参考来源

| # | 来源 | 链接 | 核心思想 |
|---|------|------|----------|
| 1 | **Neo4j Property Graph Model** | https://neo4j.com/docs/getting-started/property-graph/ | 用"节点 + 带类型的边"给业务建模，比关系表更贴近人类直觉 |
| 2 | **ReAct（Yao et al. 2022, "Reasoning and Acting in Language Models"）** | https://arxiv.org/abs/2210.03629 | Agent 按 Thought → Action → Observation 循环工作，而不是一次性生成答案 |
| 3 | **W3C OWL 2 本体语言（T-box / A-box 区分）** | https://www.w3.org/TR/owl2-overview/ | Schema（概念+约束）和 Instance（数据）必须分层管理，否则约束无法复用 |
| 4 | **LangGraph（LangChain 出品的有状态 Agent 编排框架）** | https://github.com/langchain-ai/langgraph | 把 Agent 工作流画成图（节点=步骤，边=条件分支），便于调试和复用 |

### 拿来的部分（Adopted）

- **直接复用 property graph 的节点+边建模方式**（来源 1）：
  我的 `Graph` 类就是 adjacency list 版的迷你 property graph，边带类型
  （HAS_CONTRACT / SUBSCRIBES / DEPLOYS_AT / REPORTED / AFFECTS / COVERS）。
  为什么好用：它天然能回答"这个客户的业务部署在哪个站点、那个站点现在好不好"这类
  多跳问题，SQL 要写 JOIN，图遍历一行 `out()` 就完事。
- **直接复用 ReAct 的 Think → Act → Observe → Decide 循环骨架**（来源 2）：
  `agent_handle_task()` 里四个阶段一一对应，每一步都打 trace 日志——
  这让"Agent 为什么得出这个结论"可被审计，企业客户最吃这一套。
- **直接复用 T-box / A-box 分层**（来源 3）：
  我把 6 类概念 + A1~A4 业务约束写在文件头部（T-box），
  把 13 个具体客户/合约/站点数据放在 `build_demo_graph()`（A-box），
  两层解耦——以后换数据不动规则，换规则不动数据。

### 去掉的部分（Removed）

- **去掉了真正的 Neo4j 服务和 Docker 部署**（对来源 1 的裁剪）。
  原因：我是大一学生，本机没有 Docker、没有外网拉镜像、也没有企业级数据；
  强行起 Neo4j 只会把时间花在装环境上，反而验证不了"本体 Agent 思路对不对"。
  内存图 + adjacency list 已经足够验证建模与推理链路。
- **去掉了真 LLM 调用和 API Key**（对来源 2/4 的裁剪）。
  原因：本阶段没有可报销的 API Key，也不应该在 Proposal 阶段就花钱调模型；
  Think 阶段先用规则模板占位，把**业务推理主干**跑通。
  入选后再把 Think 换成 LLM+NL2SQL，Graph 接口不变。
- **去掉了重型 OWL/RDF/TTL 序列化文件**（对来源 3 的裁剪）。
  原因：写一个 .owl 文件对我这种单人验证物是过度工程；用 Python 类 + 注释表达约束
  一样能讲清楚 T-box 是什么，而且同事能直接读。

### 重构 / 改进的部分（Improved）

- **把 ReAct 的"自由文本 Thought"重构成了结构化 trace 日志**：
  每一步输出 `[Think]/[Act]/[Observe]/[Decide]` 前缀，写入 `Trace` 对象，
  未来可以直接落库成"Agent 决策审计日志"——这是电信运营商这种行业客户
  合规审计时一定会要的东西，原始 ReAct 论文里没有这一层。
- **把 LangGraph 的"图编排"思想下沉到业务规则里**：
  我没有引入 LangGraph 这个重框架（依赖一大堆、学习成本高），
  但吸收了它"把分支条件显式画成边"的思想——
  规则 A3（站点 DOWN → site_outage）、A4（VIP → P1）都是显式的条件边，
  不是藏在 if 里的魔法数字。
- **新增了"失败分支"一等公民**：
  来源 2/4 的 demo 通常只演示 happy path；我专门写了 Case 3（陌生人）
  走 `transfer_to_human`，因为真实呼叫中心里"图里查无此人"是每天都在发生的分支。

### S（Situation）：当前问题是什么

- **现状：** 电信运营商现有客服系统是关系型库 + 人工派单，
  客户报障后要在多个系统之间人工跳转，根因定位慢、VIP 客户优先级经常漏升级。
- **痛点：**
  1. "同一个客户—合约—业务—站点"跨系统数据割裂，坐席要开 3 个界面；
  2. 故障根因靠老师傅经验，新人上手慢；
  3. 处置过程不可审计——出了投诉说不清当时为什么这么派单。
- **约束条件：**
  - 我是大一学生，每周可投入约 8–10 小时，不能影响主修课；
  - 不能动客户生产数据，早期只能用脱敏样本或合成数据；
  - 没有企业级 GPU/服务器，只能从最小可用原型起步。

### T（Task）：我要解决什么

- **核心目标：** 为电信运营商客户做出一个**基于本体的故障处置 Agent 最小闭环**——
  输入客户报障，输出根因判断 + 派单建议 + 可审计的推理轨迹。
- **子任务分解（按 8 周排期）：**
  1. **Week 1–2：本体 v1**——把客户/合约/业务/站点/工单/工程师 6 类概念和关系定死，
     产出一份《本体 v1 文档》+ 可导入 Neo4j 的 Cypher 建表语句。
  2. **Week 3–4：A-box 样本数据 + 图查询**——用 50–100 条脱敏合成数据填充，
     把本原型的内存 Graph 迁到 Neo4j Desktop（本地版，不动企业服务器）。
  3. **Week 5–6：NL2Think 接入**——把现在的规则模板 Think 换成 LLM 抽取
     （客户名 / 症状关键词 → 图查询参数），配 5–10 条回归用例。
  4. **Week 7–8：审计日志 + 一份给客户看的 Demo 包**——
     把 Trace 落库成 JSON，录一段 3 分钟演示，写一页纸业务价值说明。

### Â（Action Plan）：怎么做

| 子任务 | 具体步骤 | 用什么 AI / 工具 | 输入 → 输出 |
|---|---|---|---|
| W1–2 本体 v1 | ① 跟导师确认业务术语表 ② 用本原型 T-box 做起点 ③ 翻译为 Cypher | AI 辅助起草术语表，人工校对 | 业务名词表 → `ontology_v1.md` + `schema.cypher` |
