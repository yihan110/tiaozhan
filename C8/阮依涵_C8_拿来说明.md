## 来源 1：Neo4j Property Graph Model（属性图模型）

- **链接：** https://neo4j.com/docs/getting-started/property-graph/
- **它是什么：** 图数据库 Neo4j 的官方建模指南，规定"节点（带属性）+ 带类型的有向边"
  这种数据结构怎么表达业务。
- **我参考了什么：**
  - 节点用 `label` 区分类型（对应我代码里的 `ntype` 字段）；
  - 边必须带类型（RELATIONSHIP TYPE），不能是无类型指针；
  - 推荐"多跳查询"用图遍历而不是 SQL JOIN。
- **Adopted（采纳）：**
  - 我的 `Graph` 类 adjacency list 结构；
  - 边类型常量 `HAS_CONTRACT / SUBSCRIBES / DEPLOYS_AT / COVERS / REPORTED / AFFECTS`。
- **Removed（去掉）：**
  - 去掉了真正的 Neo4j 服务端、Cypher 查询语言、索引/约束机制。
  - 原因：本机无 Docker、无外网拉镜像时间、无企业数据；
    早期验证物的目的是验证建模思路，不是验证 Neo4j 会不会装。
- **Improved（改进）：**
  - 在边之上额外加了"业务规则层"（A3/A4）——Neo4j 文档本身只讲存储，
    不讲"节点状态变了以后业务该怎么响应"，这一层是我自己加的。

## 来源 2：ReAct（Yao et al., 2022, arXiv:2210.03629）

- **链接：** https://arxiv.org/abs/2210.03629
- **它是什么：** 论文《ReAct: Synergizing Reasoning and Acting in Language Models》，
  提出 Agent 按 **Thought → Action → Observation** 循环工作，
  而不是一次性生成答案。
- **我参考了什么：**
  - 把"想一下 → 做一步 → 看结果 → 再想"这个循环骨架；
  - Observation 必须是从环境里真实读到的东西，不能是模型编的。
- **Adopted（采纳）：**
  - `agent_handle_task()` 里的 `[Think]/[Act]/[Observe]/[Decide]` 四阶段；
  - 每一步都打 trace 日志。
- **Removed（去掉）：**
  - 去掉了"Thought 是自由文本由 LLM 生成"这一点。
  - 原因：本阶段无 API Key，也不该在 Proposal 阶段花钱调模型；
    Think 用规则模板占位，业务主干跑通后再换 LLM。
- **Improved（改进）：**
  - 把自由文本 Thought 重构成**带结构化前缀的 Trace 对象**，
    未来可直接落库成 JSONL 审计日志——这是电信运营商合规审计要的，
    ReAct 论文本身没有考虑企业审计场景。

## 来源 3：W3C OWL 2 Web Ontology Language（本体网语言）

- **链接：** https://www.w3.org/TR/owl2-overview/
- **它是什么：** W3C 制定的本体建模标准，严格区分
  **T-box（术语层：概念、属性、约束公理）**和 **A-box（断言层：具体实例）**。
- **我参考了什么：**
  - T-box / A-box 的分层思想；
  - "约束（axiom）应该写在 schema 层而不是散落在业务代码里"。
- **Adopted（采纳）：**
  - 我的代码里：6 类概念常量 + A1~A4 业务约束写在文件头部（T-box），
    `build_demo_graph()` 里的 13 个具体客户/站点数据（A-box），两层物理分开。
- **Removed（去掉）：**
  - 去掉了 .owl / .ttl 序列化文件、RDF 三元组、推理机（Hermit/Pellet）。
  - 原因：单人早期验证物写 OWL 文件是过度工程，Python 类 + 注释一样能讲清楚概念分层。
- **Improved（改进）：**
  - 把"约束"从 OWL 描述逻辑改成了**可执行的 if 规则 + 显式日志输出**
    （规则 A3/A4 命中时会打印"规则 A3 命中：…"），
    让非技术的导师/客户也能看懂这条约束触发了什么。

## 来源 4：LangGraph（LangChain 开源 Agent 编排框架）

- **链接：** https://github.com/langchain-ai/langgraph
- **它是什么：** 把 Agent 工作流建模成一张"有状态图"——
  节点是处理步骤，边是条件分支，方便调试、回放、人介入。
- **我参考了什么：**
  - "分支条件必须显式、可视化，不能藏在 if 里"这个设计哲学；
  - 每一步都有状态（state），不是无状态函数调用。
- **Adopted（采纳）：**
  - 我的业务规则全部写成显式条件边：
    `if 站点 DOWN → root_cause = site_outage`、`if VIP → priority = P1`，
    而不是混在大段代码里。
- **Removed（去掉）：**
  - 去掉了 LangGraph 整个框架依赖。
  - 原因：依赖链长、学习成本高、对大一学生本机环境不友好；
    我只需要它的"思想"，不需要它的"代码"。
- **Improved（改进）：**
  - 增加了"失败分支一等公民"——
    LangGraph 官方 demo 大多演示 happy path，我专门写了 Case 3
    （图里查无此人 → `transfer_to_human`），因为真实呼叫中心每天都在遇到这个分支。
